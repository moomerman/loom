# Example: jobsweb, a mountable dashboard

`jobsweb/` is a live dashboard for Loom's background jobs, and the
reference example of a Loom app: small, complete, and written to be read.
This walk-through shows the idioms it uses, file by file. Read
`syntax.md` and `live.md` first.

```
jobsweb/
  jobsweb.go        Config, App, New, Routes: the package's public face
  layouts.hx        Root (the document) and Shell (the sidebar)
  components.go     row types shared by pages, and small formatting helpers
  components.hx     Topbar, StateBadge, JobTable, ConfirmBar, Flash
  ui/               starter kit components (button, select, badge, ...),
                    copied with `loom components add`
  overview.go/.hx   /         queues, nodes and recent failures
  jobs.go/.hx       /jobs     filtered, paged job list
  job.go/.hx        /jobs/{id} one job, its attempts and history
  cron.go/.hx       /cron     cron entries, "run now"
  tokens.toml       its colors, spacing, radii and font sizes
  assets/icon.svg   the favicon, embedded
  *_hx.go           generated by `loom build`, committed
```

One file per page: the Go file holds the page struct and its Mount,
Events, HandleInfo and Assigns; the `.hx` file next to it holds its
template.
Markup used by several pages lives in `components.hx`. Generic controls
(buttons, selects, badges, empty states) come from the starter kit in
`ui/`, imported with `import "github.com/moomerman/loom/jobsweb/ui"`.

## Mounting

An app mounts it in one line, behind its own auth check:

```go
admin := app.Group(loom.Auth(requireAdmin))
admin.Mount("/admin/jobs", jobsweb.New(jobsweb.Config{
	ReadOnly:   func(c *loom.Ctx) bool { return !isSuperAdmin(c.Request) },
	RedactArgs: func(typ string, args json.RawMessage) json.RawMessage { ... },
}))
```

`examples/todo` does this for the user named Admin. `*jobsweb.App` is a
`loom.SubApp`: `Routes(g)` registers its pages relative to the prefix.
It also has `RequiresAuth() bool { return true }`, so mounting it with no
`loom.Auth` in the chain fails at startup (RT415): a dashboard that
deletes jobs must never be public by accident. The auth check runs on
the page load and before every event, so an admin who loses access is
stopped at their next click. See `subapps.md`.

## Routes and layouts

```go
func (a *App) Routes(g *loom.Group) {
	a.app = g.App()
	g = g.Group(
		loom.Assets(assets),
		loom.RootLayout(Root, func(c *loom.Ctx) RootAssigns { ... }),
		loom.Layout(Shell, func(c *loom.Ctx) ShellAssigns { ... }),
	)
	g.Live("/", &OverviewPage{app: a}, Overview)
	g.Live("/jobs/{id}", &JobPage{app: a}, JobDetail)
	...
}
```

- The dashboard brings its own root layout, so it looks the same in any
  host app, and an app layout (`Shell`) with the sidebar. A page tells
  the layout which nav item is current with `c.Set("section", ...)`.
- Each page value carries the `*App`, shared by every copy, to reach the
  config and the runner.
- Links use `path("/jobs")`, which resolves against the mount prefix, so
  the same templates work at `/admin/jobs` or anywhere else. A bare
  `href="/jobs"` in a `//loom:package` is warning TC336.
- The favicon is embedded with `go:embed`, served under the prefix with
  a content-hashed name, and linked with `asset("icon.svg")`.

## Templates get plain rows

Templates can only use types from their own package, with string, int,
float64 and bool fields. So each page turns `jobs.Record` and friends
into rows (`JobRow`, `QueueRow`, `NodeRow`, `AttemptRow`) in Go, formatting times
("3m ago") and numbers there. Templates stay simple, and will compile to
JavaScript later.

## Live without polling

Each page subscribes to `jobs.Topic` in Mount. Assigns runs after every
message, so the overview, the list and cron read there, and their
HandleInfo has nothing to do:

```go
func (p *OverviewPage) Mount(c *loom.Ctx) {
	c.Subscribe(jobs.Topic)
}

func (p *OverviewPage) HandleInfo(c *loom.Ctx, msg loom.Message) {}

func (p *OverviewPage) Assigns(c *loom.Ctx) OverviewAssigns {
	queues, err := p.app.runner().QueueInfo(c.Context())
	...
}
```

The runner announces changes at most every 250ms, listing the ids, and
caches queue counts between announcements, so a busy system doesn't
flood the pages or the database. The job page reads its job in `load`,
from Mount, after an action, and in HandleInfo only when
`jobs.Changed(msg.Payload, p.id)` says the message is about it; its
Assigns just formats what `load` read. Queries use
`c.Context()`, which is cancelled when the page closes.

### The Nodes panel: a topic and a timer

The overview also lists the node registry (`runner.Nodes`): each node
up or stale, a leader badge, and workers busy per queue. Nodes change on
their own topic, `jobs.NodesTopic`, every few seconds per node, so the
page reads them in `loadNodes`, from Mount and from HandleInfo for that
topic only, rather than in Assigns, where every job change would re-read
them too:

```go
func (p *OverviewPage) HandleInfo(c *loom.Ctx, msg loom.Message) {
	if msg.Topic == jobs.NodesTopic {
		p.loadNodes(c)
	}
}
```

A node that dies sends nothing, so no message says it went stale. The
page knows when it will, though: when its lease ends. `loadNodes` sets
a timer for the soonest lease of an up node (`c.SendAfter(d,
"refresh_nodes", nil)`), and each heartbeat moves it. One page-local
timer replaces polling: a dashboard nobody has open costs nothing. The
per-node stats (concurrency, done and failed in the last minute) are
labelled with the serving node's name, `runner.Node`, and the panel
marks that node "serving this page".

## Actions, confirmations, read-only

```go
func (p *JobPage) Events() loom.Events {
	return loom.Events{
		"retry":  func(c *loom.Ctx, _ loom.Payload) { p.act(c, "retry") },
		"delete": func(c *loom.Ctx, _ loom.Payload) { p.ask("delete", fmt.Sprintf("Delete job %d?", p.id)) },
		"confirm": func(c *loom.Ctx, _ loom.Payload) { ... p.act(c, p.confirm.action) },
		...
	}
}
```

- Destructive actions take two clicks: the first stores the action in
  the page's state and renders `<.confirm_bar>`; "Yes" sends `confirm`.
  No JavaScript, and the server decides what runs. Retry is safe to
  repeat, so it runs at once.
- With `ReadOnly`, the buttons aren't rendered, and `run` refuses the
  action too: events can be sent without a button.
- Every action is a `jobs.Runner` method (`Retry`, `Cancel`, `Delete`,
  `RetryDiscarded`, `RunCron`): the same ones `loom jobs` and `loom mcp`
  call, so the dashboard, CLI and agents agree. Errors are `jobs.Error`s
  whose message is shown in a flash.

## Filters and pages

The job list's filters live in the URL (`/jobs?state=discarded&queue=mail`),
so a filtered list can be shared and reloaded, the overview and sidebar
link straight to one, and the back button undoes a filter.
`HandleParams` reads them, after Mount and whenever the URL changes. The
state tabs are plain links to the same route, each built in Go from the
current filters (`Option.Href`), and following one patches the page
without a load. The queue and type selects and the search box send
`filter` with `val-field="queue"` and the value; the handler patches the
URL with `c.Patch` (`loom.Replace()` for search keystrokes), and
`HandleParams` applies it. Pages are
keyset pages of 50 by id (`jobs.Filter{Before: lastID}`): no offset and no
`count(*)`, so they stay fast on big tables.

## Styles

`tokens.toml` declares the dashboard's colors (light and dark), spacing,
radii and font sizes, including every name the kit components in `ui/`
use. Each component styles its own markup in a scoped `<style>` block with
`token(...)`; base element styles (body, links, table cells) are
`:global` rules in the root layout, the one place allowed to style
everything. Buttons, selects and empty states come from the kit; the two
controls specific to the job list, the state tabs and the compact search
box, are styled in `jobs.hx`, next to the only page that uses them. See
`components.md`.

Data never picks a raw color. Each job state has a named color in
`tokens.toml` (`state-discarded`, ...), and `StateBadge` renders
`<span class={"state" state}>`, so the state's name is the class that
picks its dot's color: a new state needs a token and one CSS rule, and an
unknown one falls back to the cancelled grey. Tests and browser tests
select on the same class (`.state.completed`).

## Testing

`jobsweb_test.go` runs each page test on the memory store and on Postgres:

```go
q := loomtest.Jobs(t)                     // or WithStore(pgjobs on loomtest.DB(t, Committed()))
q.Jobs(Email{})
app := loom.New()
app.Mount("/admin/jobs", jobsweb.New(jobsweb.Config{Runner: q.Runner()}), loom.Auth(allow))
p := loomtest.Mount(t, app, "/admin/jobs/jobs/2")
p.Listen(q.PubSub())                      // hear the runner's announcements
p.Event("retry", nil)
q.Drain(t)                                // the job runs; the page updates
p.AssertHTML(".state.completed", 1)
```

- Read-only tests send the action events anyway with `p.AssertRefused`:
  with no buttons on the page, the runtime refuses them (RT438) before
  the handlers' own read-only check.
- Behind real auth, `loomtest.Mount(t, app, path, loomtest.Cookie("user",
  "Admin"))` sends the cookie the check reads.
- `TestNodes` adds nodes with `q.Runner().Heartbeat(ctx)` and
  `q.Store().Heartbeat`, publishes on `jobs.NodesTopic` as a node would,
  and moves both clocks past a lease (`q.Advance`, `p.Advance`) to see
  the page's timer mark a silent node stale.
- `e2e/jobsweb_test.go` opens the overview in headless Chrome, enqueues a
  job and waits for it to show as completed.
